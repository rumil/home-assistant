# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **Home Assistant blueprint-publishing repo**, not an HA config directory. It tracks a single automation blueprint, `blueprints/switch-light-sync.yaml`. The live HA instance does not read this repo directly — it imports the blueprint from the file's `source_url` (the raw GitHub URL on `main`). There is no application to build, and no test/lint suite; the deliverable is declarative YAML validated by Home Assistant at import/instantiation time.

## Deploy loop (how a change reaches live HA)

1. Edit `blueprints/switch-light-sync.yaml`, commit, push to `main`.
2. In the HA UI: **Settings → Automations & Scenes → Blueprints →** the blueprint **→ ⋮ → Re-import blueprint**.

Hard constraints (do not rediscover the hard way):
- The Home Assistant MCP `ha_import_blueprint` tool **cannot overwrite** an existing blueprint, and there is no blueprint delete/override tool. The re-import is therefore a **manual UI step** — it cannot be automated from here.
- GitHub's raw CDN caches ~5 minutes; if a re-import doesn't reflect the latest push, wait and re-import again.
- After re-importing a changed blueprint, existing automation instances that use it must be re-validated. Adding a **required** input breaks every existing instance until each is updated — prefer adding new inputs with a `default:` so re-import stays non-breaking.

## Validating changes

- `python3` here has no `yaml` module. For a quick local syntax check use Ruby (it must tolerate the `!input` tag):
  ```bash
  ruby -ryaml -e 'YAML.add_domain_type("","input"){|t,v| {"input"=>v}}; YAML.load_file("blueprints/switch-light-sync.yaml"); puts "OK"'
  ```
- Real validation is HA-side. Use the Home Assistant MCP: `ha_eval_template` to test Jinja snippets against live entity state before embedding them, and `ha_get_blueprint` / `ha_config_get_automation` to confirm the live blueprint and instances after a re-import.

## Debugging a live misfire

**Start with the trace — it now states the decision outright.** The pipeline computes its classification into `variables:`, so a trace shows `intent`, `is_self_boot`, `is_recovery`, `needs_wake`, `device_originated`, `at_boot_level`, `from_on`, `target_state` and `apply_data` directly. There is no need to re-derive which path ran from timings or the recorder; read the variables block of the first `action/1` step (`action/0` is the AL re-assert `if` that precedes the `choose`, since 2026-11-19).

**The trace's `context` is the run's own context, not the triggering state's.** HA builds it as `Context(parent_id=<trigger.to_state.context.id>)`, so the trace's `context.parent_id` is the **ID** of the state change that fired the run — not that state's parent. The triggering state's own `parent_id` is not in the trace at all. Misreading this on 2026-09-28 nearly put the Adaptive Lighting marker test on the wrong field (see `unintentional_change` below). To see the triggering state's parent, find who issued the ID: e.g. an AL ID `…:al:JVQW:srvc:…` is AL's `set_manual_control` handler, whose parent is the calling automation's run context.

The `restore_previous` instances set `stored_traces: 30` (HA's default is 5), so roughly the last 30 runs are retained per automation — enough for a burst plus the events around it, but a busy morning still rotates an incident out within the hour. Once traces are gone, reconstruct from the recorder:

- `ha_get_history` on the light, the switch, **and** the instance's `input_text` store, `order="asc"`. The store's transitions show what each run decided to persist.
- `ha_get_logs(source="logbook", compact=False)` on the switch/light — `context_user_id` distinguishes a **user action** from a **device report** (firmware boot: no context at all) from an **automation's own call** (`context_domain: automation`).
- Timing fingerprints the branch when the trace is gone: an observe run is **~1.0 s**; a restore run with priming is **~11 s** (1 s settle + prime 1 s + 4 s watch + restore 1 s + 4 s watch; the `settle_time` waits add nothing when the light holds, up to 20 s each when it flaps); Scenario A is **~1.0 s**. A light-side run lasting more than a couple of seconds means `intent: restore`.
- `ha_get_logs(source="system")` — a burst of `<name>: Already running` entries means triggers are being dropped; cross-check against the desync window rather than assuming they are benign. The blueprint sets `max_exceeded: debug`, so these **no longer appear at WARNING** — an outage or restart makes `mode: single` drop dozens of self-inflicted re-entrant triggers per instance, which is by design and drowned the log. To see them, raise the level first: `logger.set_level` on `homeassistant.components.automation.<object_id>` = `debug`, then read with `level="DEBUG"`.
- Recorder/logbook timestamps come back in **local time** (Europe/Warsaw) while trace timestamps are **UTC** — do not compare them without converting.

## Blueprint architecture (`switch-light-sync.yaml`)

Two-way sync between a **Grenton virtual switch** and a **light** entity, resilient to restarts and power outages. `mode: single` — this is load-bearing: it drops the re-entrant triggers caused by the blueprint's own service calls, so scenarios can act on the light without fighting themselves.

`mode: single` cuts both ways, and the cost is not theoretical. A running scenario holds the only slot, so **any** state change landing mid-run is dropped (`execution: failed_single` in the trace) — including one that was needed to correct the state. There is no periodic reconcile, so a desync created this way persists until the next outage or user action. This makes the settle invariant below a correctness requirement, not a nicety: a scenario that reads stale state and drives an entity wrong has no second chance to fix it.

**Triggers** (each tagged with an `id`, dispatched by a top-level `choose`):
- `grenton_changed` / `grenton_recovered` — Grenton switch real change vs. return from unknown/unavailable.
- `light_changed` — light on↔off (real→real). Deliberately **not** debounced: the on/off sync must stay immediate.
- `light_recovered` — light returns from unknown/unavailable (outage recovery).
- `light_low` — `attribute: brightness` trigger with **`for: "00:00:03"`**; catches a firmware boot that drops to ~1% **without** any state-string change (these lights sometimes report 1% without going unavailable). State triggers do not fire on attribute-only changes, hence the dedicated trigger. The debounce discards the turn-on ramp (see the ramp gotcha); a genuine boot sits at 1% indefinitely, so it still fires, 3 s later.
- `light_ct` — `attribute: color_temp_kelvin` with `for: "00:00:03"`; feeds **only** the AL re-assert step below (no branch claims it). Note it also fires 3 s after **every off→on**: HA nulls the attribute while the light is off, so a turn-on is a `none → <K>` change (traces 2026-11-22). The AL-context gate is what keeps those out.
- `light_on_held` — `from: off`, `to: on`, `for: "00:00:05"`; feeds **only** the post-turn-on re-assert (opt-in `reassert_after_turn_on`), no branch claims it.
- `ha_start` — HA finished starting.

**AL re-assert (before the `choose`, 2026-11-19).** On `light_ct` whose `to_state` carries AL's `:al:` context, with the light and the switch both `on`, send one **bare** `light.turn_on`. Why: since 2026-11-19 the Z2M groups run `off_state: all_members_off` (the 16:27 incident below ruled out `last_member_state`), so a fixture that self-offs after `moveToColorTemp` but whose OFF report is lost — or a partial drop where some fixtures stay lit — leaves the group `on` with the room dark, and nothing fires. Nothing heals it later either: the TS0502B periodic messages are **Tuya `genBasic` heartbeats** (`appVersion`, attrs 65506/65508) with no onOff, and the fixtures send **no** report after a group command. Measured at Z2M debug level on living_room_track: Z2M turns a bare `{"state":"ON"}` into one groupcast `genLevelCtrl.moveToLevelWithOnOff(level=<cached group brightness>, transtime 0)` — the same command AL sends on every brightness-only adapt, which has never provoked a self-off; a fixture switched off by unicast (group still `on` in HA) came back at the right level (read back onOff 1, currentLevel 207). Checked in AL's `switch.py`: the intercept skips a light that is already `on`, and a turn_on with no brightness/colour/effect is never latched as manual control. Triggered on colour only (at night CT sits at the minimum and nothing is sent); 3 s puts it after AL's 1 s transition — a transition ≥ 3 s would be cut short. Outside the `choose`, so the run ends in milliseconds.

**Post-turn-on re-assert (`reassert_after_turn_on`, optional boolean, default off; 2026-11-22).** Same `if` as the AL re-assert (so the main `choose` stays at `action/1`), second trigger: on `light_on_held` (5 s after off→on, whoever turned it on), with the live light and switch both `on`, one bare `light.turn_on`. Why: a turn-on reaches Z2M as `{"state":"ON","transition":1.0,"brightness":…,"color_temp":…}` (AL's intercept adds colour and `initial_transition`) → moveToLevelWithOnOff + moveToColorTemp, the same provocation, and the fixtures self-off ~2–3 s later. living_room_track 13:32–13:39 (right after a Z2M restart at 13:31:27 — the documented post-re-establishment fragility, which persists while the light stays off): 4/4 turn-ons went dark; in 3, late/retried member reports (spot_2/spot_6 claimed ON at +12 s while dark) kept the `all_members_off` group `on`, so HA saw nothing. The AL re-assert *did* fire 3 s after each (see `light_ct`) but the turn-on's state carries the caller's context, not AL's — AL rewrites the call's data, not its context. Not done by dropping that gate: 3 s is too close to the drop. In the 4th (13:39:22) the group did go `off`, but its `light_changed` was dropped (`failed_single`) behind a `light_low` observe run, whose missed-self-off step re-drove it — healed by timing luck, not by the spurious-firmware-off branch. Recovery runs hold the slot past 5 s, so `light_on_held` is dropped there; the pipeline therefore sends the same bare ON at its own end on `intent == 'restore'` when the light and switch end `on` (after the save, before the AL release; the assert loop's last pass has already waited ≥ 5 s after its last drive when the restore held). **Coupling to know:** quiet recovery leaves the unprimed first on-cycle to "the next turn-on, where the spurious-firmware-off branch re-drives the drop" — that assumes the drop is *visible*, which `all_members_off` no longer guarantees; this input is what closes it. Enabled on the four track instances. Unverified: that the slot is free at +5 s on every turn-on (a `light_low` observe run ends ~+4.2 s) — check traces for `light_on_held` runs with `execution: failed_single`.

**Three branches** (top-level `choose` — **order is load-bearing**, first match wins):

- **A (`grenton_changed`)** — user action from the Grenton side. Drive the light to match the switch **immediately** (no settle up front — that would add visible lag to every wall-switch press, and is the only reason A does not share the pipeline below), then settle and save. A defend loop that held a wall-switch turn-on against the spurious post-turn-on dropout was added 2026-08-18 and **dropped 2026-09-15 (`7b25940`)**: across ~25 presses it never once re-drove a dropout, yet it held the `mode: single` slot on every press and was the main source of dropped re-presses. The spurious-firmware-off branch below now defends that dropout instead, from the light side, without the per-press cost. A also **wakes a bulb that comes up at its ~1 % firmware boot level** to the saved snapshot level (else `prime_brightness`, never the boot level itself), so a wall-switch on never ends dim; a healthy remembered level (> threshold) is left untouched.

- **Spurious firmware off (`light_changed` → `off`, `unintentional_change`, switch still `on`)** — added 2026-09-17. These TS0502B bulbs report themselves `off` **at full brightness** with no HA decision behind it minutes after a turn-on, when an Adaptive Lighting adapt with a transition lands (Z2M firmware bug [#13148](https://github.com/Koenkk/zigbee2mqtt/issues/13148)). The off carries either a context **HA minted for the report itself** (no service call within 5 s; see `unintentional_change` below), or — when it lands within ~5 s of an AL command — **AL's inherited context** (ID containing `:al:`, `parent_id` = whatever called AL), or — within ~5 s of whatever turned the light on — **that turn-on's context**. The AL form was missed until 2026-09-28. Left to the pipeline/catch-all this off is taken for the light's real state: the switch syncs `off` and the store is poisoned to `{"state":"off"}`, leaving the room dark and the next recovery restoring it dark. This branch instead **re-drives the light to the live switch until it holds**, and does **not** sync the switch off or save. Placed **before** the pipeline and catch-all (first match wins) and gated only on trigger/context/switch — no brightness read, so no settle needed to classify — so it serves **every** instance regardless of `post_outage_behavior`; the fix needs no store because it drives to the switch. A normal off carries its caller's context and falls through to the branches below — including callers with no `user_id` and no `parent_id` (Assist voice satellites, HomeKit Bridge, time-triggered automations), which the pre-2026-11-18 test mistook for the device and re-lit (office, 2026-11-18 17:25:39: a voice "turn off" reverted within ~0.3 s). It is safe where the 2026-07-22 re-assert was not (drives the **live** switch each pass, stops on a foreign change — see the re-assert gotcha and table) and does **not** revive A's dropped-re-press cost: it engages **only** on an actual device-originated off, never on an ordinary press, and settles 1 s per pass with no long drift-watch, so the slot is never held during normal traffic. `turn_on` carries no brightness or colour, so like A it never trips AL — only **`transition: 0`** (2026-09-28), so the room snaps back instead of taking AL's 1 s `initial_transition` ramp (measured: HA re-drives within 32–333 ms of the off; the remaining dark time was the ramp). Checked in AL's source: the turn_on intercept keeps a caller-supplied `transition` over `initial_transition` (AL itself omits `transition` when it is 0, and its adaptation data is merged *into* the call's params, so ours survives), and `get_light_control_attributes` — the sole manual-control test — counts only brightness/colour/effect, so transition alone never latches. This holds only while `separate_turn_on_commands` is `false` on the AL profiles (it is, on all five); if split, AL's follow-up command would carry no transition. AL's own post-turn-on `light_event` adapt still uses `initial_transition`, but it targets the values the light already jumped to (and `skip_redundant_commands` drops it once state matches), so it should not be visible. Cross-run self-heal: a second firmware drop ~3 s later re-fires `light_changed` and re-enters, paced by the firmware, which drops for one cycle before the ON sticks. That drop carries the previous re-drive run's context (parent set) and is recognised by clause 3 of `unintentional_change` (same context turned the light on); before 2026-11-18 it read as intentional.

- **The light-side pipeline (`light_changed | light_low | light_recovered | ha_start`, when `restore_previous` and `has_store`)** — recovery, self-boot and ordinary user actions are the same physical situation seen at different moments, so they share one implementation with a single branch point:

  ```
  settle (delay 1s + wait for brightness)
  classify → intent = restore | observe
  target  := snapshot (restore) | current light state (observe)
  prime    (restore, threshold > 0, prime_allowed) + settle
  assert   (skipped when there is nothing to assert; settle each pass, ≤ 5 drives)
  missed self-off (observe: light went off mid-run, unintentional, switch on → re-drive, stop)
  sync switch  (restore → target_state unless yielded; observe → the light)
  save     (observe only)
  re-assert (restore ended on, switch on, reassert_after_turn_on → one bare turn_on)
  al release (restore or needs_wake, when has_al and light on)
  ```

  **Missed self-off (2026-11-19).** The observe path syncs the switch from the light read ~1 s after its trigger, and any off that lands in that second has its own `light_changed` dropped by `mode: single` — the spurious-firmware-off branch never sees it. living_room_track 16:27:41: the ON echo of a spurious-off re-drive started an observe run, a late member OFF (same context) arrived 41 ms later, and under `last_member_state` the run synced `switch.living_room_ceiling` off and saved `{"state":"off"}`; the fixtures stayed lit for 3 h on a stale colour with HA, Grenton and AL all believing them off. Now, before the sync, an observe run whose light went `off` with the switch `on` applies `unintentional_change` to the live state with the run's trigger `to_state` as from_state (all three clauses, inlined — keep in lockstep); device → one `turn_on transition: 0` and `stop` (no sync, no save; the echo starts a new run that checks again). `all_members_off` already makes a lone late member harmless, but the all-member post-turn-on drop (1.08 s after an ON that same minute) can still land inside the settle.

  `intent == 'restore'` writes the **light from the store**; `intent == 'observe'` writes the **store from the light**. They are inverse data flows, which is why both must exist: drop the save and nothing ever learns what "previous" means; always restore and you can never switch a light off.

  Classification happens *inside* the branch, not in `conditions:` — the boot test needs a brightness reading, and the state string arrives ~1.5 s before the attribute, so a condition would read the value before it exists.

  The **`al release`** step is last, after the save, and runs only when `has_al` and the light ended **on**. Every attributed `light.turn_on` this branch issues — priming, the snapshot restore, the `needs_wake` brightness — is seen by Adaptive Lighting (with `take_over_control` on) as a manual override, so AL stops adapting the light until it is turned off and on again; a light left on after an outage then sits frozen at the recovery colour/brightness for hours. `adaptive_lighting.set_manual_control` (`manual_control: false`, scoped to this light via `lights:`) clears that flag and hands colour/brightness back to AL. It sits **after** the save on purpose: `needs_wake` is `intent == 'observe'`, so the save runs on that path too, and releasing AL first would let it start re-adapting before the save reads state — snapshotting a mid-adapt value. Gated on `intent restore or needs_wake` because only those paths attribute the light; **Scenario A's bare `turn_on` sends no attributes and never trips AL**, which is why it needs no release. Skipped when the restore ends `off` (bare `turn_off`, nothing to have latched). See the AL gotcha below.

- **Catch-all (`grenton_recovered | light_changed | light_recovered | ha_start`)** — must stay **last**. The light is source of truth; sync the switch to it. Takes Grenton's own recovery (handled nowhere else, relevant to every instance) plus everything the pipeline declined: `light_source_of_truth` instances, and `restore_previous` instances with no store configured. **`light_changed` is deliberately duplicated here** (it is also a pipeline trigger): the pipeline is gated on `restore_previous and has_store`, so on a source-of-truth instance an ordinary light-side on/off matches the pipeline branch's trigger but fails its condition, and without this it would land in no branch — light→switch sync silently dead. This regressed in `27eb974` (the pre-collapse Scenario B synced `light_changed` ungated for every instance) and broke light→switch sync on every source-of-truth instance until re-added. `light_low` is **not** added — a boot-level brightness drop leaves on/off unchanged, so the sync would be a no-op; brightness/priming is restore_previous-only. First-match-wins means restore_previous instances still take `light_changed` in the pipeline, never here.

**Intent classification** (all visible in the trace):
- `is_recovery` — trigger was `light_recovered` or `ha_start`.
- `is_self_boot` — the bulb powered itself up: went **off → on**, at a **readable** brightness ≤ threshold, and `device_originated`. The light never went unavailable so no recovery trigger fired, but physically it is the same event and gets the same treatment.
- `device_originated` — equals the top-level `unintentional_change`, the **single definition** of "nothing in HA decided this", evaluated on `trigger.to_state` (2026-11-18). True when any of:
  1. **minted context** — `user_id` and `parent_id` null **and** the context ID's ULID time (first 10 chars, Crockford base32, decoded with `ulid_alphabet`) equals `last_updated` to ±1 ms. HA stamps a service call's context on the entity and reuses it for every write within 5 s (`helpers/entity.py`, `CONTEXT_RECENT_TIME_SECONDS`); only when no call touched the entity for 5 s does `StateMachine.async_set_internal` mint `Context(id=ulid_at_time(timestamp))`. Measured live: every pure device report diff 0 ms, every commanded state 120–530 ms, the satellite off 4.5 s (its context dates from the wake word).
  2. **AL off** — the state is `off`, `user_id` null, and the context ID contains AL's marker `:al:` (`al_context_marker`).
  3. **same-context on→off** — `off`, `from_state` was `on` in the **same** context, and `from_state.last_changed` ≥ that context's ULID time (the context turned the light on). Covers the post-turn-on firmware drop inheriting whatever did the turn-on — voice, HomeKit, this automation's own re-drive/restore, a wall press, the HA app. The `last_changed` test keeps a fade-off (dimming `on` reports in the off's context first) intentional. Not covered: one script run that turns a light on and then off within 5 s while the switch is on reads as the device.
  The live-state copies (both repeat loops' foreign test and `yielded`) carry clauses 1–2 only (no `from_state` there); keep them in lockstep. If HA ever stops minting contexts this way, clause 1 fails toward "intentional": firmware offs get synced off again, a deliberate off is never reverted. Re-check after an HA upgrade by decoding a light's `states[...].context.id` against `last_updated` with `ha_eval_template`.
  - Why not `user_id`/`parent_id`: a Grenton wall-switch press reaches the light through Scenario A with `user_id` null but `parent_id` stamped, so `user_id` alone took it for a device report; and an **anonymous** caller has neither — the satellite pipeline uses `context or Context()` (`assist_satellite/entity.py`) and the intent handler calls the service with it, HomeKit does `Context()` per call (`homekit/accessories.py`), and a time trigger passes no context so the automation runs in `Context(parent_id=None)`. `user_id`+`parent_id` null was the test until 2026-11-18 and reverted every such off with the switch on.
  - Why the AL exception (2026-09-28, `hall_track`, trace `ab9beeee`): `automation.track_lights_al_grace_period` cleared `manual_control`, AL adapted, and the group self-offed 1 s later. HA attributes any state write within 5 s of a service call to that call's context, so the off carried AL's context: ID `01M3MD705G:al:JVQW:srvc:1C`, `parent_id` = the grace-period run. With a parent set it was taken as intentional — the pipeline synced the switch off and saved `{"state":"off"}`. AL never calls `light.turn_off` (checked in its source), so an off in its context is always the device.
  - Why **off only**: after every turn-on AL adapts via `create_context("light_event", parent=<the turn-on's context>)` — an ON in AL's context with `user_id` null is routinely the tail of a user action. Counting it as unintentional would let `needs_wake` fight AL's night brightness (≤ threshold).
  - AL's format (from `create_context` in `custom_components/adaptive_lighting/switch.py`): `"<10-char ULID time>:al:<base32 name hash>:<which minus vowels>:<base36 index>"`, 26 chars; AL's own `is_our_context_id` tests for the same `:al:` substring. If an AL upgrade changes this, the exception silently stops matching — re-check the source.
- `needs_wake` — an observe-path boot-level drop (the light was already on and sank). Corrects **brightness only**, never on/off.

**Persistence model:** the "saved state" is a JSON snapshot written to a per-instance `input_text` helper (`state_store` input) via `input_text.set_value`, and read back with `from_json`. This is deliberate: an HA automation **cannot** create a persistent scene (`scene.create` is wiped on restart) or create helpers at runtime, so the store helper is provisioned separately and passed in as an input. `saved_attributes` (input) selects which light attributes to snapshot; the save loop skips any the light reports as `none`. Saves never persist a non-on/off state, an unreadable brightness, or a low brightness that is not a deliberate dim (see the ramp gotcha).

**`post_outage_behavior`** has only two values: `light_source_of_truth` (default) and `restore_previous`. `turn_on`/`turn_off` were removed in `27eb974` — unused by every live instance. The pipeline is gated on `restore_previous and has_store`, **not** on the threshold, so `recovery_brightness_threshold: 0` disables boot detection and priming only; the snapshot is still restored on recovery.

**Restart hardening (2026-10-05).** A plain HA Core restart (host up, lights powered) once ended a restore to `{"state":"off"}` with the living room lit: three priming `turn_on`s made the 9-member Z2M group (`off_state: last_member_state`) flap for ~15 s, the assert loop burned its 3 tries mid-flap, the sync read a transient `on` 20 ms old and turned the switch on, and `grenton_changed` made it stick. Three changes, all in the pipeline:
- **`host_boot_sensor`** (optional timestamp sensor, e.g. System Monitor "Last boot") + **`host_boot_window`** (min, default 10) → `prime_allowed`. On `ha_start` priming runs only when the host booted within the window; empty input or no valid timestamp fails safe to priming (old behaviour). `light_recovered`/self-boot always prime. Only priming is gated; the restore drive always runs. **No such sensor exists on the live instance yet** — until one is added and wired into the instances this gate is inert.
- **Settle** (`settle_time`, s, default 3): after priming and after each assert pass, poll every 0.5 s (≤ 40 polls = 20 s) until `last_changed` is `settle_time` old. A `repeat`/`while` with `now()` in a condition, **not** a `wait_template` (`now()` there re-renders once a minute). The assert loop now judges the **settled** state and allows 5 drives (was 3).
- **Sync on restore follows `target_state`**, never the momentary light — unless `yielded` (the assert loop's foreign test on the live state: a user or another automation took over), in which case the light is the intent and the switch follows it. Observe is unchanged.
- The foreign test (assert loop + `yielded`) also treats a context whose **parent is this run** as ours: AL's post-turn-on adapt carries our context as parent and would otherwise read as "another automation". The spurious-firmware-off loop still lacks this clause.
- Not covered: on 2026-10-05 16:21 the restore ended correctly, then the group flapped `on` **0.8 s after the run freed the slot**; the observe path synced the switch on and saved `{"state":"on"}`. The settle does not catch a flap that starts after a quiet watch window — `prime_allowed` (no priming → no flap) is the fix for that, so it needs the boot sensor configured.

**Quiet recovery (`quiet_recovery`, optional boolean, default off; 2026-11-09).** Off = exactly the behaviour above. Built after the 2026-11-09 power cut: the host booted 08:59:48, the router came up late, Z2M restart-looped until 09:02:00, and Mosquitto persistence replayed the pre-outage retained `bridge/state` "online" and groups "off" to HA at 09:00:48. The 09:01:29 `ha_start` recovery primed three times into a dead Z2M (the dropout watch completes at once on the stale "off"), found state == target, and "succeeded"; the fixtures stayed at their power-on glow. Bedroom recovered only because its group has no retained state (stayed `unknown` → `light_recovered` at 09:02:12). When on:
- **Priming gate on every recovery path:** `light_recovered` is gated by the host-boot window too, not just `ha_start` (`prime_allowed`). For Z2M groups `light_recovered` never means a lone fixture dropped: in 10 days the track groups went unavailable only with the bridge, and every Z2M restart/update (e.g. 04:52, 04:10) primed and flashed the rooms at night; a group without retained state also came back from `unknown` ~40 s after every plain HA restart and primed. Self-boot still primes.
- **Delivery check + wait for Zigbee:** on `ha_start`/`light_recovered` inside the host-boot window, the first command is checked: delivered = the light's `last_updated` moved after it (Z2M publishes a group's state as soon as it sends the command). The check must change what the light reports: target on → the first prime (`prime_brightness − 1` if it already reads on at exactly that level); target off and reads on → `turn_off`; target off and reads off → ON at the threshold (the boot-level glow). Undelivered → `wait_for_trigger` (light report or wall press) up to 10 s, re-check, until delivered or the window ends; then fire the event `switch_light_sync_recovery_failed` (`light`, `switch`, `waited_s`) and `stop` with no restore/sync/save (trace: `delivered: false`) — the event is the only reliable "Z2M never came up" signal, since the bridge connection sensor replays a stale retained "online". Delivered → `final_command`: the assert loop's first pass commands the goal even when the light already reads it (a `last_member_state` group can read `off` while fixtures glow, and the confirming report may not have come from the check). `bridge/state` is deliberately not used: its retained "online" replays on every HA start and automation reload and can be stale, and an mqtt-triggered run would race this one under `mode: single`.
- **`follow_switch`:** a wall press during the wait (its own `grenton_changed` is dropped) makes the live switch the target: the assert loop re-reads it every pass and drives bare on/off, and the sync is a no-op. Set from inside the loop by a `variables` step — HA updates the outer variable from inside a nested block (documented on the Define variables page); every `until` inlines the expression rather than relying on that.
- **Prime only when the restore ends ON:** a real prime is a bright ON, which at night is a flash in a room about to go dark. A restore to OFF gets only the boot-level delivery check, then `turn_off`. The bulbs' fragile first on-cycle is then left to the next turn-on, where the spurious-firmware-off branch re-drives the drop (a blink while awake instead of a flash while asleep), and Scenario A's wake lifts the remembered boot level. If that drop inherits Scenario A's context (within 5 s of the press), clause 3 of `unintentional_change` (same context turned it on) still reads it as the device (since 2026-11-18).
- **Quiet tail:** both settles measure `last_updated` (any report) for `settle_need` = max(`settle_time`, 6) s. **Every run of this automation has `user_id` and `parent_id` null in its own context — `ha_start` included (trace `992bb727`)** — so under the pre-2026-11-18 test its commands' echoes looked device-originated; 6 s exceeds HA's 5 s context reuse, so none outlives the run as a fake spurious-off or self-boot (the 1→252→255 ramp included). The minted-context test now reads those echoes as ours anyway; the tail stays because it also keeps a flapping group's late reports inside the slot. The tail sits before the AL release, so an AL post-adapt self-off still lands after the run and is re-driven.
- Not covered: a wall press during the ~15 s prime/assert *after* delivery (or in any recovery run without a prior wait) is still dropped, as before.

**`adaptive_lighting_switch`** (optional, `default: ""`) — the Adaptive Lighting instance's main switch (e.g. `switch.adaptive_lighting_main`) governing this light. Gated by the `has_al` variable (same shape as `has_store`) and referenced via a template, not `!input` (the optional-entity gotcha — an empty `!input` in a service `target:` fails config-load on every instance). When set, the pipeline's `al release` step clears AL's manual-control flag for this light at the end of a recovery. Non-breaking: instances that leave it empty behave exactly as before. Live instances map to different AL profiles, so it is per-instance (office → `switch.adaptive_lighting_main`). Added 2026-09-17.

## Blueprint conventions / gotchas

- **There are two distinct ways these lights turn themselves off. Do not conflate them — they have opposite culprits.** Diagnosed 2026-07-20/21 over a long investigation that went down the wrong path twice.
  - **(A) Spurious device dropout — the blueprint is innocent.** *Every* group member reports `state: OFF` **at full brightness** (255, not the 1 % boot level) and Z2M computes the group as off. In the traces `at_boot_level`/`is_self_boot`/`needs_wake` are **false**, `cur_bri` is **255**, no `light.turn_off` appears anywhere, and the HA `off` state carries a context HA **minted for the report** (`user_id`/`parent_id` null and the ID's ULID time == `last_updated`) — this device-originated context is the load-bearing signature. `user_id`/`parent_id` null alone is **not** the signature: voice satellites, HomeKit and time-triggered automations produce it for deliberate offs. **Exception:** when the drop lands within 5 s of an AL command it carries AL's context instead (ID with `:al:`, a parent set), which `unintentional_change` also treats as the device. It has **two provocations**, same firmware fault (Z2M [#13148](https://github.com/Koenkk/zigbee2mqtt/issues/13148), TS0502B; the manufacturer is `_TZ3210_xbnztn5i`, no OTA path):
    - **Post-turn-on burst.** ~3 s after the first turn-on following a Zigbee re-establishment. It only bites when several groups are switched **in a rapid burst** (the first light switched always survives; the 2nd/3rd/4th drop), and **the fragility does not expire** — it persists for as long as the light stays off, so a 00:14 recovery still ambushed the first turn-on at 11:26. This is what the pipeline's **priming loop** absorbs, and on 2026-07-22 it absorbed a four-instance simultaneous recovery burst — the exact provoking load — without consuming a single retry.
    - **Post-adapt, minutes later (diagnosed 2026-09-17).** An Adaptive Lighting adapt carrying a real CT change with a non-zero `transition` lands ~5 min after a turn-on; the group drops off **at the end of the transition**, groupcast to all members at once. Signature `intent: observe` / `target_state: off` — with the switch still `on`, the pipeline would sync the switch off and poison the store. Now claimed by the **spurious-firmware-off branch** (device-originated off + switch on → re-drive to the live switch, no sync-off, no save). The user keeps `transition` and adds no adapt delay, so this branch is the accepted plaster; the firmware fault itself is unfixable without OTA. A sharper variant (2026-09-28): the grace-period automation clearing `manual_control` makes AL adapt **immediately**, and the drop lands ~1 s later — inside AL's 5 s context window. Known open risk: every re-drive is an off→on, which re-arms the 15-min grace period, whose end re-adapts and can drop the light again — a possible ~15-min cycle across runs (each run is still capped at 3 passes). Not mitigated in the blueprint yet; log-only detection or a cooldown were proposed.
  - **(B) The boot heuristic hijacking a user turn-on — the blueprint's fault.** If the bulb genuinely comes up at 1 % (`cur_bri: 1`, common right after a Z2M/HA restart) the heuristic fires and "restores" the snapshot; when that snapshot is `{"state":"off"}` it **switches off a light the user just turned on**. Caught red-handed in a trace on 2026-07-21.
  - This was once believed unfixable by tightening the user test, on the theory that a post-restart device report carries no user context even when the user did initiate the turn-on. **That theory is wrong** — disproven 2026-07-22 across many traces, where `device_originated` came out **false** on every genuine user action, including turn-ons moments after a Z2M restart. What was actually missing was `parent_id`: `user_id` alone cannot see a Grenton wall-switch press, which arrives through Scenario A with `user_id` null and a parent stamped. Requiring **both** to be null was a sound test against users and wall presses but not against anonymous callers (voice, HomeKit, time triggers) — since 2026-11-18 the minted-context test gates the self-boot restore (the AL exception in `unintentional_change` applies to offs only, so it cannot make a turn-on look like a self-boot). The old structural rule still holds on the observe path — `needs_wake` corrects brightness only — but on/off restores are no longer confined to the unavailable-recovery trigger.
- **Adaptive Lighting latches every *attributed* `light.turn_on` as a manual override — the recovery path must hand control back.** These lights are under AL with `take_over_control: true` / `take_over_control_mode: pause_all` / `autoreset_control_seconds: 0`. Any `light.turn_on` carrying `brightness`/`color_temp_kelvin`/etc. that is not AL's own marks the light `manual_control` and AL stops adapting it — and with `autoreset_control_seconds: 0` the flag never expires on its own; it clears only when the light is turned off and on again. The recovery pipeline sends attributes in three places (priming, snapshot restore, `needs_wake`), so **every recovery of an AL light silently freezes its colour** until someone power-cycles it. Diagnosed 2026-09-17: `office_track` stuck at 6097 K from noon because a Zigbee dropout at 12:52 recovered and restored `{brightness: 255, color_temp_kelvin: 6097}`, which AL took as manual. Fix is the `al release` step (`adaptive_lighting.set_manual_control` `manual_control: false`) at the branch end, gated on `has_al`. **Scenario A never had this problem** because it drives the light with a *bare* `turn_on` (no attributes) and the AL instances have `manual_control_on_external_turn_on: false` — a bare external `turn_on` is not taken as manual. So the rule is: on an AL light, any path that sends attributes owes AL a release; a bare on/off does not. Accepted tradeoff for AL instances: the restored brightness/colour is immediately overwritten by AL's next adapt, so `saved_attributes` there is effectively just on/off + priming — which is the intent, since AL owns colour. The **root cause** (office dropping off the mesh ~5×/week, `office_track_linear_3` at LQI 0) is untouched by this; the release masks the AL symptom, not the mesh.
- **Priming the bulb and making the restore stick are two separate problems.** The pipeline has **two** retry loops and needs both. The first proves the bulb accepts an ON; the second re-asserts the *restored* target state until it holds. Verifying only the first is not enough: on 2026-07-21 office primed cleanly, took a correct `turn_off`, and then flipped back on **3.7 s later** because the group members disagreed (`linear_1` reported `OFF` while the spots reported `ON`, and Z2M computes a group as on when **any** member is on). Staying inside the run for that second loop is half the fix — it holds the `mode: single` slot so the spurious flip's `light_changed` is *dropped*; once the run had ended, the user-action path took the flip for a user action, synced the switch on and wrote `{"state":"on"}` into the store.
- **Never re-assert against a *frozen* target, and never against a change HA did not cause — a loop that cannot tell noise from intent is not a correction loop, it is a fight.** Learned expensively on 2026-07-22 (`6684f88`): a re-assert loop added to Scenario A "for consistency" switched off a light the user had just turned on, 3 s after they turned it on (trace `0ce61722`: iteration 1 commanded nothing because the light already matched, the drift watch then *completed* when the user turned it on, and iteration 2 dutifully "corrected" it). It fired constantly because A runs on every Grenton change **including the switch sync the pipeline itself performs**, so routine activity parked the automation in a 4 s watch window with the `mode: single` slot held — which also swallowed the user's own `light_changed`. The fix is **not** "never loop in A"; it is that a loop here must (1) drive the light to the **live switch** each pass rather than a captured target — the switch is the user's intent, so a re-press is always honoured and the light is never stranded disagreeing with it — and (2) re-drive **only** our own echo or an unintentional device flip, using the same foreign-change test below, so it cannot revert a deliberate action. Scenario A carried such a defend loop from 2026-08-18 until it was dropped on 2026-09-15 (`7b25940`); today the loops that follow this rule are the **spurious-firmware-off branch's re-drive** and the **pipeline's assert loop**. Both stop on a foreign change — anything that is neither this run's echo nor `unintentional_change` applied to the live state —

  | origin | the light's context | re-assert? |
  |---|---|---|
  | our own command | this run's `context.id` (HA reuses it for the device echo, 5 s), or — assert loop only — a context whose parent is this run (AL's post-turn-on adapt) | yes |
  | spurious device flip | minted by HA for the report (no user, no parent, ID time == `last_updated`) — or an **off** whose ID carries AL's `:al:` | yes |
| anonymous caller (voice satellite, HomeKit, time trigger) | no user, no parent, but **not** minted | **stop** |
  | user action | `user_id` set | **stop** |
  | another automation | a parent that is not ours | **stop** |
- **The turn-on ramp is not one event.** Z2M publishes a turn-on as a sequence of brightness messages — `1 → 252 → 255` over ~10 s measured on these groups — each one its own `light_low` trigger. Before `b55405a` a single turn-on produced four runs and wrote `{"brightness":1}` then `252` then `255` into the store. The low value survived the save guard because the guard only asked "did a user cause this", the carve-out for a deliberate dim to 1 %. **You cannot dim a light you just turned on** — a real dim requires `from_on`, so a low reading on an off→on transition is always the ramp caught mid-flight, whoever initiated it. Persist a brightness ≤ threshold only when `from_on and not device_originated`. Usually the next run overwrote the bad value, so this only bit if a turn-on was the last event before an outage — the store would hold `1` and the next recovery would restore the room to 1 %.
- **A poisoned store is silent and self-perpetuating.** It only shows up on the *next* recovery, as the light being restored to the wrong state. When a recovery ends wrong, check `input_text.light_sync_*` before re-deriving anything.
- **Never let the priming level reach the snapshot.** The save is gated on `intent == 'observe'` for exactly this reason, and the re-entrant triggers priming generates are dropped by `mode: single` while the run holds the slot. If you let a save reach the restore path, the priming level becomes the "previous" state and the next recovery restores the light to it.
- **`prime_brightness` must stay above `recovery_brightness_threshold`.** The priming loop's "did it drop out?" test treats *at or below threshold* as a dropout, so priming at or under the threshold makes the loop think it failed every time and burn all its retries.
- **The priming level is also the level the bulbs *remember*.** These bulbs retain the last level they were commanded to and light up at it on a plain `light.turn_on` with no `brightness`. So after a recovery that ends with the light off, the last thing they were told was the priming level — and that is what the next manual turn-on lights up at. Priming at 10 % (the original default of 25) left every fixture coming on dim; hence the default is now **255**. If you ever lower it to make the recovery flash subtler, expect that dimness to resurface on the next plain turn-on.

- **`context.user_id` inside an automation is always `none` — it can never detect a user action.** HA builds an automation's run context as `Context(parent_id=<trigger context id>)` and does **not** copy `user_id` into it. Any `context.user_id is none` test is therefore unconditionally true and is dead code. Use **`trigger.to_state.context.user_id`**, which does carry the real user: HA's entity service call stamps the calling context onto the entity, and subsequent `async_write_ha_state()` calls reuse it for `CONTEXT_RECENT_TIME` (5 s) — long enough that even the *later* MQTT state/attribute messages from Z2M still carry it. This is why the logbook and the trace disagree: the logbook resolves attribution by walking the parent chain and shows the real `context_user_id`, while the automation reads the raw value and sees `null`. Do not diagnose this from the logbook alone. Cost of getting it wrong: the boot heuristic in the old Scenario B fired on deliberate user turn-ons and "restored" the light to the saved snapshot (`{"state":"off"}`) ~3.5 s later, across all four instances (fixed 2026-07-16). Note `trigger.to_state.context` is also where **`parent_id`** lives, which is the half that distinguishes an automation-driven change from a device report — see the intent classification above. The same 5 s reuse cuts the other way too: a device self-off inside that window inherits whoever commanded the light last — for AL lights that is AL itself, hence the AL exception in `unintentional_change`.
- **A light attribute that is absent reads as `none`, and `| int(0)` turns that into a real `0`.** HA reports *every* light attribute as `none` while the entity is off, and for a moment after it turns on. So `state_attr(light, 'brightness') | int(0) <= threshold` is **true for an unreadable brightness**, and any "is it dimmed to ~1%?" test silently becomes "…or did we fail to read it?". Always require `state_attr(...) is not none` alongside the threshold compare. Diagnostic that proves it in one shot: `ha_eval_template` the old and new forms side by side against an off light — old yields `True`, new `False`.
- **Waiting for the state string is not waiting for the attributes.** Z2M publishes a group's `state` and its `brightness` in separate MQTT messages; the gap was measured at **1.53 s** on these groups, so the old fixed `delay: "00:00:01"` sampled while brightness was still absent. Wait for the reading itself (`wait_template` on `state_attr(...) is not none`, guarded by `not is_state(..., 'on')` so an off light passes straight through). Keep the fixed settle **as well** — the two solve different problems: the settle guards against reading an *intermediate* value the light is about to leave, the wait guards against reading *no* value at all. Collapsing them into one re-opens the other hole.
- **Settle after every service call before reading the state it changes.** `light.turn_on`/`turn_off` return as soon as the command is dispatched; the entity keeps reporting its *old* state until the device round-trips (MQTT/Zigbee: ~100–500 ms). A `condition: state` evaluated straight after a light command reads the pre-command value. Every restore→sync path therefore settles between the command and the read; the old Scenario B's boot path silently lacked it until 2026-07-16 (fixed in `836978b`), which drove the Grenton switch to the state the light was *leaving* and — because `mode: single` then dropped the correcting `light_changed` — stranded a switch `on` against a light `off` for 2h10m. **If you add a branch that commands an entity and then reads it, settle in between.** The same reasoning applies to the brightness read the pipeline's classification depends on (the 1 s at the top) — Zigbee groups report `state: on` first and the `brightness` attribute ~500 ms later, so reading immediately sees `brightness: 0` and can misfire the boot test. Since `27eb974` there is **one** settle definition and **one** boot-level definition shared by every path; before that there were three of each, honoured inconsistently (`prime_brightness` was respected on one path out of three, and the single-shot restore in the old Scenario D was a latent repeat of the 2026-07-21 flip-back).
- Target lights are **Zigbee2MQTT groups** (`platform: mqtt`, `unique_id: <n>_light_zigbee2mqtt`) — Z2M publishes the group as its own MQTT light and computes group state itself. The `group_entities` attribute is Z2M metadata, not an HA group-helper member list, so those member entity_ids may not resolve in HA (they are deliberately disabled on the live instance) and carry no recorder history. This does not affect the group's behaviour. Group `off_state` is **`all_members_off`** on all four track groups since 2026-11-19 (it was `last_member_state` from 2026-09-29): with `last_member_state` one late member report flips the group, and Z2M then keeps that state — on 2026-11-19 the living room group read `off` for 3 h while every member's heartbeat still said ON. The cost of `all_members_off` (a group reads `on` while some or all fixtures are dark) is what the AL re-assert covers.
- **Read the Zigbee2MQTT add-on log — it is the per-fixture trail HA does not have, and it shows values HA actively hides.** `ha_get_logs(source="supervisor", slug="45df7312_zigbee2mqtt", search="<device_or_group_topic>")`. It carries every member's raw payload (`brightness`, `color_mode`, `color_temp`, `linkquality`, `state`) plus the computed group topic. Reach for it **early**, alongside `ha_get_history` / `ha_get_automation_traces`, on any Zigbee issue — the recorder cannot substitute: `ha_get_history` elides most attributes, and HA nulls *every* light attribute while the entity is off, so a device's real reported values are visible nowhere else. Two 2026-07-16 diagnoses turned on it: the per-device `brightness` proved a "1% boot" reading was actually an unread `brightness: None` (the office bulbs were demonstrably at 254 yet still took the boot path — impossible unless `cur_bri` read 0), and the per-device `color_mode: "hs"` explained why a group's `color_temp_kelvin` was permanently `none` (one `hs` member poisons the group's computed mode, which HA then rejects against `supported_color_modes: ["color_temp"]` — look for `Invalid color mode 'hs' received` at WARNING). It is also the fastest way to confirm a fix at the device level rather than through HA's interpretation of it.
- **Optional `entity` inputs must be referenced via a template, not `!input`.** An unset entity input defaults to `""`; if `!input` puts that empty string into a service `target: entity_id:`, HA fails config-load validation for *every* instance (checked at load, regardless of runtime guards). Use `entity_id: "{{ some_var }}"` and gate the call on a `has_store`-style guard instead. See `state_store` for the pattern.
- Bind inputs to `variables:` and use the variable inside Jinja — `!input` is a YAML tag, not a template value.
- Light color attributes use `color_temp_kelvin` (mireds-based `color_temp` was removed in HA 2026.3).
- Keep `source_url` stable — it is the re-import anchor.
